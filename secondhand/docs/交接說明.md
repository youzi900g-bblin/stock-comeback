- 開發分支只有一個：`claude/secondhand-clothing-game-design-trv0hj`，只推這個分支；沒有使用者明說，不開 PR。

## 二、使用者偏好與工作流程（必須遵守）

1. 繁體中文（台灣用語），正式、精煉、具體；不編造數字、名稱、日期，沒有來源就問。
2. 只改被要求的地方，不順手改設計、配色、結構。
3. **流程（已定案）**：使用者先說 → 我先回覆「打算怎麼改」，內容與設計類（髮型、配色、款式、版型、文案）列成編號選項並附建議 → 使用者確認後才修改 → 改完並測過（含截圖檢查）後才更新試玩網址並推送。使用者說「直接做」「照建議」視為確認。工程類操作（git、整理檔案）可以直接做。
4. 大任務先給簡短計畫，計畫要短，不要列一堆問題。
5. 使用者的電腦常打不開線上站，所以改完要截圖給他看；但他明說「不用畫全部總覽」時就不要傳總覽。
6. 他說「之後再說」的事不要追著推。他常反覆調整，改版前先確認是哪一版（例如「涼鞋 3」「涼鞋 4」），舊版都在 git 歷史裡可以還原。
7. 已安裝 ponytail skill（`.claude/skills/`）：用最小而完整的改動，回覆結尾用一兩行說明跳過了什麼或有什麼風險。
8. 發布網址已長期授權，但只在使用者確認過修改之後；排程做出來的草稿不更新網址。
9. **檢查要粗略、不重複（使用者明確要求）**：目前階段只要確認「不會壞」；只檢查這次改到的地方，看改到的那個畫面的截圖就好，不要把所有畫面重看一遍。已經驗證過、而且這次沒動到相關程式的東西，不要重跑，也不要重複確認。改到共用的部分（例如角色圖層）才跑一次圖層比對（`check_layers.py`）與 NPC 圖逐位元組比對。使用者會非常多次修改，所以每做完一項，記住哪些已驗證過。
10. 版面或美術類的改動，使用者習慣「先看示意圖（圖片）→ 確認 → 才改程式」；他也會自己在圖上手繪或直接修改像素圖給我，要逐格照他的圖做（林的圖就是這樣做的）。
11. 使用者一次可能同時回覆好幾題，回覆「照建議」「全部照建議」就是全部採用我的建議；訊息可能是語音輸入，有錯字時（例如把「照建議」打成「小建議」）先照最合理的意思理解並說明。

## 四、驗證方式（每次都要）

1. `python3 tools/pixel_art/build_art.py` 重新輸出。
2. `python3 tools/pixel_art/check_layers.py` → `mismatch 0`。
3. NPC 四張圖（`三位角色`、`三個臉`、`眼睛嘴巴組合`、`雀斑_各膚色`）與未刻意改動的場景圖，與 git 上原圖逐位元組相同（`cmp`）。
4. `python3 tools/qa/qa_sprite.py /tmp/exp.json && node tools/qa/qa_sprite.js /tmp/exp.json` → `{"bad":0}`。
5. `SP=截圖資料夾 node tools/qa/qa_ui.js`：手機與桌機無橫向溢出、觸控目標不小於 44px、無主控台錯誤。
6. 放大看過輸出圖，再看實際顯示大小。

## 七、已知問題與風險

- 衣服的零星孤立點：開襟衫、涼鞋腳踝、托特包把手、後背包頂部各有幾格；使用者說不用再動。

- 沒有做過真機與螢幕閱讀器測試；`design:accessibility-review`（Anthropic 的 Design 外掛）使用者尚未啟用。
- 涼鞋已經改過多版，目前是「涼鞋 4」：一條橫帶、一列純皮膚色、鞋面、有花紋的鞋底。

- `art/player/face.js` 會隨款式增加變大（目前約 76 KB）。
- 連帽 T 單獨取出（縮圖）看起來像背包，因為圖層是穿在身上的輪廓；之後可考慮另畫掛在衣架上的版本。
- 社群貨與創角衣物沒有對應基本款樣板的款式，標籤與基礎價值沿用同類型第一個樣板，標籤可能不貼切（例如運動外套顯示「優雅」），皆為佔位。
- 私人衣櫃的「放回」按鈕因格子窄而縮短，意思可能不夠清楚，使用者尚未表示意見。
- 賣家名稱、貼文文案、愛心與留言數是佔位示意；愛心與留言目前只是顯示，不能點。
